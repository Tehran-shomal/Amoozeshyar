# نتیجه‌ها و منع عملیات (PDF-only reference states)

- مرجع: PDF صفحهٔ ۳۰ (منع به علت بدهی)، ۳۸–۴۸ (نتایج عملیات)، ۵۶–۵۹ (نتایج حذف/اضافه). صفحات ۷۵–۷۸ فهرست حذف اضطراری با داده‌های متفاوت‌اند، نه صفحهٔ نتیجه.
- route/owner: نتیجه‌های صفحه‌های ۳۸–۴۰ از workflowهای کارآموزی، مهمانی و پیام می‌آیند؛ صفحهٔ ۴۱ بعد از POST تنظیمات از Person حساب جاری رندر می‌شود؛ صفحهٔ ۴۲ از GradeAppeal، صفحهٔ ۴۳ از ScholarshipApplication، صفحه‌های ۴۴–۴۵ از StudentServiceRequest و صفحهٔ ۴۶ از Ticket ریشهٔ متعلق به حساب جاری استفاده می‌کنند. صفحات ۵۶–۵۹ از ثبت جدید register و Enrollment فعال مالک‌محور در `/portal/add-drop/?registration_id=...` استفاده می‌کنند. نتیجهٔ حذف موفق با `dropped_enrollment_id` در همان route و فقط برای Enrollment حذف‌شدهٔ همان Student/Term خوانده می‌شود.
- رفتار موجود: خطاهای mutation به کد/message JSON و پیام UI تبدیل می‌شوند؛ موفقیت register فقط اگر API `created=true` برگرداند به نتیجه می‌رود؛ retry فعال با `created=false` موفقیت جدید اعلام نمی‌کند. صفحهٔ ۳۰ خطای واقعی `tuition_debt` را در modal داخل انتخاب درس نمایش می‌دهد. صفحه‌های ۳۸–۴۶ نتیجه‌های کارآموزی، مهمانی، پیام، تنظیمات، اعتراض نمره، تسهیلات، درخواست دانشجویی، درخواست گواهی و تیکت را از دادهٔ ذخیره‌شده نشان می‌دهند؛ صفحه‌های ۵۶–۵۹ Enrollment ثبت‌شده را نشان می‌دهند؛ حذف عادی/اضطراری نتیجهٔ scoped دارد. تخصیص وام، تأیید اعتراض، تحویل پشتیبانی یا صدور مدرک ادعا نمی‌شود. صفحهٔ ۴۷ پرداخت واقعی ندارد؛ صفحهٔ ۴۸ پیش‌نمایش گواهی PDF را به سند رسمی تبدیل نمی‌کند.
- داده/API: `POST /api/enrollment/register/<id>/`, `POST /api/enrollment/drop/<id>/`, و emergency-only `POST /api/enrollment/emergency-drop/<id>/`; Enrollment/Term/Student متعلق. `tuition_debt` و سقف از Student خوانده می‌شوند؛ حداقل واحد از مدل/API موجود نیست.
- اعتبارسنجی/مجوز: rule checks در service؛ بدهی مانع ثبت‌نام است؛ حذف مجاز به بازه‌های تعریف‌شده.
- محدودیت‌ها: modal صفحهٔ ۳۰ با `tuition_debt` واقعی باز می‌شود؛ لینک «پرداخت بدهی» به secure-payment می‌رود که نبود درگاه را اعلام می‌کند؛ مقدار ۱۲ PDF به‌عنوان حداقل جاری نمایش داده نمی‌شود چون حداقل در قواعد کد تعریف نشده است. صفحات ۳۸–۴۰ عملیات بیرونی را تأیید نمی‌کنند و درخواست مهمانی هنوز نیازمند review است؛ صفحهٔ ۴۱ تنظیمات را واقعاً ذخیره می‌کند اما سرویس اعلان ترجیح را اعمال نمی‌کند. حذف status را عوض می‌کند، ولی API بازپرداخت را محاسبه/ثبت نمی‌کند.
- آزمون: `apps/core/enrollment/test_services.py`, `static/core/tests/portal_api.test.cjs`, `portal_bindings.test.cjs`.
- آزمون صفحات ۳۰ و ۳۸–۴۲: regressionهای template/JS و مالکیت نتیجه‌های عملیاتی نوشته شده‌اند ولی اجرا نشده‌اند. نتیجهٔ حذف هم test مالکیت Student/Term دارد؛ **NOT RUN**.
- وضعیت: نتیجه‌ها از رکورد واقعی و scope مالک ساخته می‌شوند؛ مرجع PDF مرور شده اما تطبیق runtime ترتیبی هنوز به صفحهٔ ۱۹ نرسیده است.
