# طرح جداسازی فرانت‌اند و استفاده از داده‌های seed

## هدف

کد فرانت‌اند پورتال در پنج ماژول مالکیت تیمی تقسیم شود تا هر گروه manifest صفحه‌ها و selectorهای خودش را داشته باشد. شاهسوند و امید یک گروه کد «خدمات آموزشی» می‌سازند، اما فهرست صفحه‌های هرکدام در manifest و README جدا می‌ماند. مقدارها و رکوردهای قابل نمایش دیگر از fixtureهای داخل فرانت نیایند؛ هیچ رکورد نمایشی، fallback نمونه یا مقدار ساختگی در کد فرانت اضافه نشود.

این تغییر مرجع داده را عوض می‌کند، اما هدف قبلیِ حفظ طراحی پورتال و پنج گروه منو پابرجاست. عنوان‌ها، متن راهنما، نام دکمه‌ها و تنظیمات ظاهری متن رابط کاربری هستند و برای نمایش خود صفحه باقی می‌مانند؛ اطلاعات دانشجو، درس، شهریه، درخواست، پیام و اعلان فقط از رکوردهای دیتابیس می‌آیند. اگر برای یک صفحه رکوردی وجود نداشته باشد، جدول/فهرست آن خالی نمایش داده می‌شود و رکورد نمونه جایگزین نمی‌شود.

## یافته‌های وضع فعلی

- `apps/core/frontend/<group>/pages.py` مرجع مالکیت، عنوان و metadata صفحه‌هاست؛ `registry.py` manifest پنج گروه کد را برای routeها یک‌جا اعتبارسنجی می‌کند.
- `apps/core/templates/core/live_content.html` قالب عمومی صفحه‌های داده‌محور است؛ فقط صفحه‌هایی با markup اختصاصی قالب جدا دارند.
- فایل ریشهٔ `seed_data.py` رکوردهای مدل‌های پروژه را می‌سازد. فرمان جداگانهٔ `python manage.py seed` یک مولد عمومی دادهٔ تست است و برای این تغییر منبع داده محسوب نمی‌شود.
- خواندن ORM در این محیط نشان داد که جدول‌های `Student`, `Term`, `CourseOffering`, `Enrollment`, `Grade`, `Payment`, `Ticket`, `Communication`, `Notification` و `StudentServiceRequest` فعلاً رکورد ندارند. این طراحی seed را اجرا نمی‌کند یا رکورد دامنه‌ای نمی‌سازد؛ پیش از اجرای seed، صفحه‌های داده‌محور خالی‌اند. migration منشأ فقط در صورت تأیید جداگانه ساخته/اجرا می‌شود.
- مدل‌های فعلی منشأ هر رکورد را ذخیره نمی‌کنند؛ پس query معمولی به‌تنهایی نمی‌تواند رکورد seed را از رکورد دیگری تشخیص دهد.
- helper موجود `current_student` در `apps/core/accounts/services.py` می‌تواند پروفایل دانشجویی متصل به `request.user` را resolve کند. دسترسی به داده‌ها باید فقط به همین دانشجو محدود شود.

## محدوده

### هدف‌ها

- جداسازی مالکیت صفحه و داده‌خوانی بر اساس پنج گروه کد؛ پنج گروه منوی محصول مستقل می‌مانند.
- حذف داده‌های fixture از `portal_data.py` و ساخت context صفحه‌ها فقط از ORM و رکوردهای فعلی دیتابیس.
- محدودکردن تمام queryهای شخصی به دانشجوی واردشده؛ هیچ رکورد دانشجوی دیگری نباید در صفحه‌ها بیاید.
- حفظ مسیرها، APIهای فعلی ثبت/حذف درس، کلاس‌های CSS و ساختار کلی صفحه.
- حفظ متن‌ها، ترتیب و چیدمان UI فعلی؛ رکوردهای نمایش‌داده‌شده فقط به داده‌های دیتابیس تغییر می‌کنند.
- نوشتن کامنت کوتاه و خوانا برای مسئولیت هر گروه و منطق query که بدیهی نیست.

### خارج از محدوده

- اجرای `seed_data.py` یا `python manage.py seed`، تغییر محتوای seedها، یا ساخت رکورد دانشجویی/آموزشی تازه.
- ایجاد API، endpoint یا capability جدید.
- وارد کردن fallback یا ردیف نمونه برای صفحه‌هایی که رکورد منطبق ندارند.
- افزودن نام یا سابقهٔ ساختگی برای تیم‌های دانشجویی.
- تغییر مسیرها و endpointهای موجود؛ اصلاح markup و CSS فقط برای تطبیق صفحه‌های ناهماهنگ با PDF مجاز است.

## پنج گروه ناوبری محصول

نام پوشه‌ها در تمام لایه‌ها با underscore یکسان است تا نام بسته‌های Python نیز معتبر باشد.

| کلید پوشه | عنوان گروه | مسیرها |
| --- | --- | --- |
| `academic_finance` | وضعیت تحصیلی و مالی | `academic-activities`, `transcript`, `payments`, `tuition`, `secure-payment`, `financial-aid` |
| `registration` | ثبت‌نام و انتخاب واحد | `enrollment`, `selected-courses`, `add-drop`, `emergency-drop`, `registration-status`, `grade-appeal`, `curriculum` |
| `academic_planning_exams` | برنامه آموزشی و امتحانات | `internship`, `attendance`, `calendar`, `schedule`, `exam-card` |
| `requests_permissions` | درخواست‌ها و مجوزها | `requests`, `education-certificate`, `graduation-certificate`, `guest-request`, `graduation` |
| `student_communication_services` | ارتباط و خدمات دانشجویی | `evaluation`, `evaluation-form`, `messages`, `announcements`, `student-card`, `notifications`, `settings`, `guide`, `support` |

صفحه‌های پنهان در منو مثل `selected-courses` و `evaluation-form` در گروه مالک خود باقی می‌مانند. گروه‌های ناوبری با پوشه‌های مالکیت کد یکی نیستند؛ `NAV_GROUPS` در metadata مشترک می‌ماند.

## پنج گروه مالکیت کد فرانت

| پوشه | مالکیت |
| --- | --- |
| `mobina` | ورود، داشبورد، انتخاب واحد، دروس انتخاب‌شده، چارت انتخاب واحد |
| `shaghayegh` | حذف و اضافه، حذف اضطراری، وضعیت ثبت‌نام، اعتراض به نمره |
| `academic_services` | **شاهسوند:** ارزشیابی، فرم ارزشیابی، ارتباط با استاد، درخواست مهمانی، فارغ‌التحصیلی؛ **امید:** فعالیت آموزشی، کارنامه، حضور و غیاب، کارت امتحان، درخواست‌های دانشجو و مدارک |
| `parsa` | سوابق پرداخت، پرداخت امن، تسهیلات، مالی نیمسال‌ها |

هر یک از پنج پوشه `pages.py`, `selectors.py` و `README.md` دارد؛ `academic_services/pages.py` علاوه بر فهرست routeها، `MEMBER_PAGES` را برای تفکیک مالکیت شاهسوند و امید نگه می‌دارد. ورود و داشبورد به‌عنوان صفحه‌های ویژه در ماژول مبینا ثبت می‌شوند؛ `term_picker` مؤلفهٔ مشترک ماژول لید است. قالب عمومی و رفتار مشترک در مسیرهای `apps/core/templates/core/` و `static/core/` می‌مانند. صفحه‌هایی مثل کارت دانشجویی، کارت امتحان و جریان‌های ثبت‌نام که در PDF markup ویژه دارند، قالب صفحه‌ای در گروه مالک خود می‌گیرند؛ مقدارهای قالب فقط از selector و رکوردهای واقعی می‌آیند.

## منبع و مالکیت داده

- رکوردها از دیتابیس خوانده می‌شوند؛ خود seed فایلِ قابل import برای نمایش نیست و نباید در هر request اجرا شود.
- `seed_data.py` ریشه تنها منبع مجاز برای ایجاد رکوردهای seed است. محتوای آن عوض نمی‌شود؛ فقط باید ثبت منشأ رکوردهای تازه‌ساخته‌شده به آن اضافه شود.
- برای تضمین منشأ، طرح نیازمند یک registry سبک مانند مدل `SeededRecord` با شناسهٔ `ContentType` و `object_id` است. seed فقط رکوردهایی را در آن ثبت می‌کند که خودش همین بار ساخته؛ رکوردهای ازپیش‌موجود که `get_or_create` پیدا می‌کند seed فرض نمی‌شوند.
- migration مربوط به registry فقط schema/شناسهٔ منشأ را اضافه می‌کند؛ رکوردهای دامنه‌ای seed نمی‌سازد و seed را اجرا نمی‌کند.
- queryهای داشبورد و صفحه‌های دانشجو باید بر اساس `request.user` و Student record متصل به آن فیلتر شوند. اگر کاربر وارد نشده یا پروفایل دانشجویی ندارد، دادهٔ شخصی نمایش داده نمی‌شود و از `Student.objects.first()` یا کاربر دیگری fallback نمی‌گیریم.
- داده‌های فعلی میان مدل‌ها تقسیم شده‌اند: مشخصات و خلاصهٔ تحصیلی از `Student`/`Person`; برنامه، انتخاب واحد و کارنامه از `Term`, `CourseOffering`, `Enrollment`, `Grade`, `Attendance` و `Curriculum`; امور مالی از `Payment`, `TuitionReceipt` و `Student.tuition_debt`; درخواست‌ها از مدل‌های درخواست موجود مثل `Ticket`, `StudentServiceRequest`, `ScholarshipApplication`, `TransferRequest`, `GraduationAudit` و `InternshipRequest`; ارتباطات از `Communication`, `Notification` و `TeacherSurvey`.
- هر صفحه فقط از مدل مرتبط خودش داده می‌گیرد. برای موردی که در دیتابیس یا seed مدل/رکورد منطبق ندارد، بخش داده‌ای خالی می‌ماند؛ از متن PDF ردیف دادهٔ جدید ساخته نمی‌شود.
- اعداد و تاریخ‌های دیتابیس را می‌توان برای نمایش قالب‌بندی کرد، اما مقدار معنایی یا ردیف جدید نباید از کد ساخته شود.

## ساختار نهایی فرانت‌اند

```text
apps/core/frontend/
  common.py                                  # کمک‌تابع‌های قالب دادهٔ مشترک
  metadata.py                                # پنج گروه ناوبری، footer و متن ورود
  registry.py                                # تجمیع و اعتبارسنجی manifestهای تیمی
  views.py                                    # ورود، داشبورد و routeهای بخش
  mobina/{pages.py,selectors.py,README.md}
    templates/mobina/{home.html,login.html}
    static/mobina/section.js
  shaghayegh/{pages.py,selectors.py,forms.py,README.md}
    static/shaghayegh/section.js
  academic_services/{pages.py,selectors.py,forms.py,README.md}
    templates/academic_services/{student_card.html,exam_card.html,...}
  parsa/{pages.py,selectors.py,forms.py,README.md}
  neyousha_pouya/{pages.py,selectors.py,forms.py,README.md}
    templates/neyousha_pouya/notifications.html
apps/core/templates/core/
  portal_base.html, section.html, live_content.html, database_unavailable.html
static/core/
  portal.css, responsive.css, portal_api.js, live_portal.js
```

`apps/core/portal_data.py` حذف شده است. `HomeView` از queryهای کاربر جاری برای خلاصهٔ داشبورد استفاده می‌کند؛ `PortalSectionView` slug را به ماژول مالک نگاشت می‌کند و از selector همان گروه context را می‌سازد. قراردادهای URL و endpoint فعلی حفظ می‌شوند. صفحه‌ها به‌صورت پیش‌فرض از قالب مشترک استفاده می‌کنند؛ metadata می‌تواند برای صفحهٔ دارای markup واقعی، قالب اختصاصی تعیین کند.

`portal.css`, `responsive.css`, `portal_api.js` و `live_portal.js` رفتار و سبک مشترک را نگه می‌دارند. اسکریپت‌های ثبت/حذف درس کنار گروه مالک هستند؛ فایل CSS اختصاصی فقط در صورت وجود استایل ویژهٔ واقعی اضافه می‌شود.

## گزینه‌های بررسی‌شده

1. **دادهٔ ثابت همراه ساختار پنج‌گانه:** فایل‌های UI جدا شوند اما fixtureهای `portal_data.py` باقی بمانند. سریع‌تر است ولی با درخواست تازهٔ کاربر که حذف دادهٔ نمونه را می‌خواهد سازگار نیست.
2. **جداسازی گروهی با خواندن رکوردهای دارای منشأ seed (انتخاب کاربر):** هر گروه manifest صفحه و selectorهای خودش را دارد؛ قالب مشترک برای داده/فرم‌های یکسان می‌ماند و قالب یا asset جدا فقط برای نیاز واقعی ساخته می‌شود. هیچ fallback ساخته نمی‌شود.

## محدودیت‌ها و ملاحظات اجرا

- دیتابیس فعلی در این محیط خالی است. تا زمانی که کاربر خودش seed را اجرا نکند، خالی‌بودن صفحه‌ها رفتار مورد انتظار است؛ برای پر کردن صفحه، فرانت نباید ردیف جایگزین بسازد.
- فرمان عمومی `manage.py seed` منبع این تغییر نیست؛ seed root نیز در این پیاده‌سازی اجرا نمی‌شود.
- برخی routeهای فعلی (برای نمونه راهنما، گواهی آموزشی، پرداخت امن یا اعلان استاد) مدل یا رکورد معادل در root seed ندارند. ظاهر و route می‌توانند بمانند، ولی محتوای داده‌ای‌شان نباید از fixture قبلی حفظ شود.
- توابع query باید فقط خواندنی باشند و هیچ side effect یا ساخت رکورد نداشته باشند.
- چون دیتابیس فعلی خالی است، registry با migration جدید آغاز می‌شود؛ هیچ دادهٔ قدیمی برای حدس‌زدن منشأ وجود ندارد.
- متن UI، title، label، icon و empty state صرفاً اجزای رابط هستند؛ هیچ مقدار دانشجویی یا مورد فهرست‌شده‌ای نباید با متن hard-coded پر شود.

## معیار پذیرش

- پنج ماژول تیمی صفحه‌هایشان را در manifestهای محلی تعریف کنند؛ پنج گروه ناوبری در metadata مستقل باقی بمانند.
- `academic_services.MEMBER_PAGES` مسئولیت‌های شاهسوند و امید را بدون هم‌پوشانی ثبت کند.
- routeهای منو و صفحه‌های پنهان هر کدام دقیقاً یک مالک داشته باشند؛ registry route تکراری یا بدون مالک را رد کند.
- قالب عمومی برای محتوای تکراری استفاده شود و هیچ wrapper مشترک یا CSS خالی در پوشهٔ تیم‌ها باقی نماند.
- فرانت هیچ import یا استفاده‌ای از `DEMO_STUDENT`, `DASHBOARD`, `PORTAL_PAGES`, داده‌های درس/پرداخت/پیام fixture یا سایر رکوردهای `portal_data.py` نداشته باشد.
- هر رکورد شخصی فقط وقتی نمایش داده شود که هم متعلق به دانشجوی واردشده باشد و هم در registry به‌عنوان ساخته‌شده توسط root `seed_data.py` ثبت شده باشد.
- در نبود رکورد، فهرست خالی باشد؛ هیچ fallback یا مقدار تستی ساخته نشود.
- اجرای migration منشأ، seed script، URLها و endpointهای فعلی بدون تأیید کاربر انجام نشود.
- محتوای رکوردها با دیتابیس یکسان باشد؛ فقط قالب نمایش محلی مجاز است.
- login/logout و API فعلی انتخاب/حذف درس حفظ شوند و ترتیب بارگذاری اسکریپت‌ها درست بماند.
- هیچ تغییر بصری عمدی در ساختار و CSS صفحه‌ها ایجاد نشود؛ محتوای داده فقط از منبع fixture به ORM منتقل شود.

## تصمیم‌های واگذار‌شده به مجری

- انتخاب نام helperها و روش dispatch برای پنج ماژول تیمی، با نگاشت ثابت و بدون import پویا از slug کاربر.
- دسته‌بندی CSS مشترک و اختصاصی بر اساس markup واقعی.
- انتقال queryهای چندمدلی به selectorهای ساده و خوانا؛ بدون ایجاد endpoint یا abstraction اضافی.
- به‌روزرسانی assertion تست موجود که مسیر asset مشترک را بررسی می‌کند، بدون حذف پوشش رفتار فعلی.
